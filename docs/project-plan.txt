--------------------------------------------------------------------------------
1. WHAT THIS PROJECT IS (IN ONE PARAGRAPH)
--------------------------------------------------------------------------------
The Pearls AQI Predictor is an end-to-end, 100% serverless machine-learning
system that forecasts the Air Quality Index for Lahore three days into the
future. It automatically collects weather and pollution data every hour,
transforms it into model-ready features stored in a feature store, retrains
forecasting models every day, and serves live predictions through a public web
dashboard. The whole thing runs on free infrastructure with no server to manage
- data collection, training, and serving are all automated.


--------------------------------------------------------------------------------
2. WHY IT MATTERS (THE PROBLEM)
--------------------------------------------------------------------------------
* Lahore is repeatedly ranked among the most polluted cities on Earth. Its AQI
  regularly exceeds 150-200 (Unhealthy) and spikes far higher during winter smog.
* A reliable 3-day forecast lets residents - especially children, the elderly,
  and people with respiratory conditions - plan ahead (limit outdoor activity,
  use masks/air purifiers).
* In machine-learning terms this is a TIME-SERIES REGRESSION / FORECASTING
  problem: predict a continuous AQI value at future time steps using weather +
  pollution history and calendar features.

4. HOW THE SYSTEM WORKS (ARCHITECTURE)
--------------------------------------------------------------------------------
The system is built as four decoupled pipelines connected through a central
Feature Store + Model Registry. This is the well-known "FTI" (Feature / Training
/ Inference) architecture.

  Open-Meteo API            (raw weather + pollutants)
        |
        v   (hourly)
  [1] FEATURE PIPELINE  ->  fetch -> compute features -> store
        |
        v
  HOPSWORKS FEATURE STORE   (single source of truth for features + targets)
        |                                   ^
        |  (daily)                          |  features + targets
        v                                   |
  [2] TRAINING PIPELINE ->  train -> evaluate -> register best model
        |
        v
  HOPSWORKS MODEL REGISTRY  (versioned models + their metrics)
        |
        v   (on demand)
  [3] WEB APP / INFERENCE -> load model + features -> show 3-day forecast

  [0] BACKFILL PIPELINE (one-off): replays the feature pipeline over 2+ years of
      history to create the initial training dataset.

WHY DECOUPLE? Each pipeline can run, fail, and scale independently. The feature
store is the clean interface between them, so no pipeline needs to know how any
other one works. This is what makes the system "production-grade," not just a
notebook.

5. TECHNOLOGY STACK (AND WHY EACH CHOICE)
--------------------------------------------------------------------------------
  DATA SOURCE     : Open-Meteo (Air Quality + Weather APIs)
     Why: Free, needs NO API key, serves BOTH history and forecast. Perfect for
     an unattended serverless pipeline (no secret to manage).
     Alternatives: AQICN / OpenWeather (need API keys; some limit history).

  FEATURE STORE   : Hopsworks (free tier)
     Why: Purpose-built for serverless ML; includes a Model Registry; versioned
     features prevent "train/serve skew."
     Alternatives: Vertex AI (needs GCP billing, heavier); plain CSV (no
     versioning, no upsert, no single source of truth).

  ORCHESTRATION   : GitHub Actions
     Why: Truly serverless, free, version-controlled, with a visible run history
     that PROVES the automation is live.
     Alternatives: Apache Airflow (needs a server to host - not serverless).

  CLASSICAL ML    : scikit-learn + XGBoost
     Why: Industry standard; XGBoost is very strong on tabular data.

  DEEP LEARNING   : TensorFlow (LSTM)
     Why: Handles temporal sequences; required by the brief ("statistical to
     deep learning"). PyTorch would be equally valid.

  EXPLAINABILITY  : SHAP
     Why: Game-theoretic, model-agnostic feature-importance with rich plots.
     Alternative: LIME (local only, less consistent).

  WEB APP         : React frontend + FastAPI backend
     Why: React gives a far more polished, interactive UI (maps, custom charts)
     than Streamlit, and FastAPI satisfies the brief's "Flask/FastAPI" option.
     Kept serverless: a daily GitHub Action PRE-COMPUTES forecasts for all cities
     into a predictions store/JSON, and the React app just reads them (a live
     backend is only needed for the optional LLM advisor).
     (Streamlit remains a fast fallback if the React path runs low on time.)

  LANGUAGE / ENV  : Python 3.11 + conda
     Why: 3.11 has the best compatibility with TensorFlow and the Hopsworks SDK
     (3.13 is too new for some of these libraries).

  VERSION CONTROL : Git (+ GitHub)
     Why: Professional history; also the trigger surface for GitHub Actions.

6. OUR APPROACH (HOW WE ARE ACTUALLY DOING THIS)
--------------------------------------------------------------------------------
WORKING METHOD
  * The project is built MODULE BY MODULE, in coherent chunks - not all at once.
  * After each chunk is built, tested live, and documented, there is a pause to
    STUDY it before moving to the next chunk. Goal: be able to defend every line
    and design choice in the interview.
  * Every piece of code is verified on REAL Lahore data before we move on
    (e.g. a bug was caught by cross-checking our AQI against Open-Meteo's).
  * Everything is documented in docs/interview-prep.md as we go, so nothing is
    left out and the final report writes itself.

ENGINEERING PRACTICES
  * Clean, installable "src/" Python package (pip install -e .) for tidy imports
    everywhere (local, CI, app).
  * Secrets via a gitignored .env file locally and GitHub Secrets in CI - never
    committed.
  * Split requirements (core / app / deep-learning / dev) so CI stays fast.
  * Unit tests for the tricky logic (AQI math, feature engineering).
  * Git commits per logical unit with clear messages.

KEY DATA-SCIENCE PRINCIPLES WE FOLLOW
  * Prevent TARGET LEAKAGE: every lag/rolling feature is shifted so it only uses
    the past, never the current/future value.
  * Use TIME-SERIES-CORRECT evaluation (walk-forward validation), never a random
    train/test split that would leak the future.
  * Always compare models against a simple BASELINE (e.g. "tomorrow = today") so
    complexity is justified by real improvement.
  * Cross-validate computed values against an independent source.
